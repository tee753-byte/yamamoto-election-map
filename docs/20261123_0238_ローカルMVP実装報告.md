## 2. 実装した機能

### ログインと権限

- Supabase Authによるメール・パスワードログイン
- 管理者、作業担当者、閲覧のみの3権限
- 非ログイン利用者をログイン画面へ移動
- 画面表示だけでなく、DBのRLSとRPCでも権限を確認
- 一般利用者による新規登録を停止

RLSは「Row Level Security」の略で、データベース側で利用者ごとに読める行・変更できる行を制限する仕組みである。

### ポスターマップ

- 地理院タイルで福津市を表示
- 架空の掲示場20件
- 未対応、担当中、完了、要確認の4状態
- 状態フィルター、掲示場詳細、状態更新、現在地への移動
- 状態別件数と完了率
- 共通の掲示場と候補者別作業を分離したDB構造

画面は山本ゆうへいさんだけだが、同じ掲示場へ候補者別の作業レコードを追加できる。
石田まなみ議員との合同作業は未確定のため、候補者レコードを追加していない。

### ポスティングマップ

- 架空の配布区域6件
- 状態、担当者、目標数、配布済み数
- 状態フィルター、区域詳細、状態・配布数更新
- 状態別件数、完了率、配布済み合計
- 管理者が有効期間を設定できるDB構造
- 期間外・無効時の更新拒否
- 同一操作IDの再送による配布数二重加算の防止

試作の活動期間と説明は適法性の確認結果ではない。実運用前に陣営が文書・期間・方法を確認し、設定を更新する。

### 安全性と復旧性

- 全内部テーブルでRLSを有効化
- クライアントから利用者IDや権限を受け取らず、サーバー側セッションを使用
- `version` 番号を比較し、古い画面からの上書きを拒否
- 状態更新と操作履歴を同じDB処理で実行
- 架空データを `supabase/seed.sql` から再作成可能
- 秘密キーをアプリへ使用せず、`.env.local` をGit対象外に設定

Supabase統合テストでは、次を実際のローカルDBで確認した。

- 非ログインでは内部データを取得できない
- 閲覧者は更新できない
- 作業担当者のテーブル直接更新をRLSが遮断する
- 作業担当者は割当済みの作業だけRPC経由で更新できる
- 担当外の更新は拒否される
- 古い版番号の更新は競合として拒否される
- 同じ配布操作を再送しても配布数・版番号は1回だけ増える
- 正常な更新が操作履歴へ残る
